## 1. DNS 泄露（实测证据）

```
① 53 端口劫持：dig @8.8.8.8 / @192.168.31.1 / @223.5.5.5 / @1.1.1.1 doubleclick.net
   → 四个全部返回空（说明查询都进了 sing-box 的 DNS 规则，而不是真的发到那些解析器）

② 出口回显：dig TXT o-o.myaddr.l.google.com
   → 系统解析器与 @1.1.1.1 都返回 172.64.212.11（Cloudflare 的解析出口）
   → 海外域名由 Cloudflare DoH 经代理解析，ISP 看不到

③ 明文 DNS：ss -un / -tn 里没有任何指向外部 :53 的套接字
   → 没有 UDP/53 明文外发（sing-box 走 DoH over 443）
   现存 53 监听者只有本机服务：127.0.0.53/54（systemd-resolved）、192.168.122.1（libvirt）

④ 国内解析：ss 显示到 223.5.5.5:443 的 DoH 连接
   → 国内域名走阿里 DoH（不是明文 UDP，比之前那版更强）

⑤ resolvectl：tun0 = 172.19.0.2 / fdfe:dcba:9876::2，DNS Domain ~.
   → 系统解析器 100% 指向隧道
```

**唯一残留面**：`dns.servers` 里那个 `dns-local`（`type: local`）现在没人引用；一旦将来被误引用，就会绕过 DoH 走系统解析器 → 建议直接删掉。

**一个天然限制（你已规避）**：`hijack-dns` 只覆盖 53 端口/`dns` 协议，浏览器自作主张的 **DoH（443）不经过 sing-box 的 DNS 规则**。
好在你的广告拦截**同时写在 `route.rules` 里**（连接层按 sniff 出的域名 reject），所以即使用户开浏览器 DoH，
广告连接照样被 RST —— 这个"双写"设计是对的，别只留 DNS 那一条。

## 4. 问题清单与改法（按优先级）

### P1 —— 广告覆盖缺口
加 anti-AD 规则集（`~/.cache/sing-box-rule-sets/anti-ad.srs` 已生成，待 `sudo cp` 到 `/etc/sing-box/rule-set/`）：

```jsonc
// route.rule_set 追加
{ "type": "local", "tag": "anti-AD", "format": "binary", "path": "/etc/sing-box/rule-set/anti-ad.srs" }

// dns.rules 第 1 条 与 route.rules 第 4 条，rule_set 都追加 "anti-AD"
{ "rule_set": ["geosite/category-ads-all", "Ads_AWAvenue", "anti-AD"], "action": "reject" }
```

### P1 —— geoip/cn 过期（实测 8.130.222.0/24 走了代理）
上游最新 `geoip/cn.srs` 含 **9,648** 条 CIDR 且包含 `8.130.0.0/15`（本地那份 8,045 条缺）。两条路：

1. **刷新系统包**：`sudo pacman -Syu sing-geoip-rule-set`（当前 20260912，落后 3 周）；
2. **本地双保险**：把上游最新文件放 `/etc/sing-box/rule-set/geoip-cn-fresh.srs`，加第二个 local 规则集，路由里改成
   `"rule_set": ["geoip/cn", "geoip/cn-fresh"]`。

> 长期方案（很契合你已有的仓库）：在 `~/pkgbuild-source` 里加一个 **`sing-box-rule-sets`** 包，
> 用 CI 定时拉 MetaCubeX geosite/geoip + anti-AD，转成 `.srs` 打包安装 —— 规则集就跟系统更新一起滚动，不用手工维护。

### P2 —— 1.14 弃用告警（1.16 会移除）
```

```
正好和「去掉 MetaCubeXD」一起处理（见 `singbox-panel-guide.md` §9）。

### P2 —— 3 个 DNS 服务器无人引用 + 可做故障转移
`dns-proxy-google`、`dns-direct-tencent`、`dns-local` 都没被任何规则引用。
**这个 fork 实测支持 `type: group`**（上游 1.14 不支持，fork 有），所以可以把它们变成故障转移组：

```jsonc
{ "type": "group", "tag": "dns-proxy",  "servers": ["dns-proxy-cf", "dns-proxy-google"] },
{ "type": "group", "tag": "dns-direct", "servers": ["dns-direct-ali", "dns-direct-tencent"] }
// dns.final 与相关 dns.rules 改指向这两个组；dns-local 直接删除（潜在泄露面）
```

### P3 —— 两条冗余路由规则
`route.rules` 第 11 条（`protocol quic + port 443 → Proxy`）与第 12 条（无条件 `→ Proxy`）都与
`route.final = Proxy` 重复，可删（少两条规则匹配）。

### P3 —— 可选性能优化
`store.steampowered.com` / `cdn.steamstatic.com` / `www.microsoft.com` 现在都走代理（`geolocation-!cn`）。
本地规则集里已有 `geosite-steam@cn.srs`（还有 microsoft 相关），若你下载 Steam 游戏/Office 觉得慢，
可加一条 `geosite/steam@cn → direct`（CDN 直连通常快数倍）。**这是偏好项**，不是问题。

## 7. 外部规则源评估：[HenryChiao/mihomo_yamls](https://github.com/HenryChiao/mihomo_yamls)（用户提供）

实测结论：**这个仓库能直接供 sing-box 用**（不是只有 mihomo 格式），而且有两点很有价值。

### 7.1 它发布现成的 sing-box 规则集
`ruleset` 分支下 `singbox/version1..version4/` 各 **104 个分类**（`adrules` / `ai` / `cn` / `cncidr` / `gfw` / `games` / `microsoft-cn` / `apple-cn` / `private` / `proxy` / `netflix` / `spotify` …），
每个分类同时给 `.json`（源）与 `.srs`（二进制），**每天 07:30(UTC+8) 自动重建**。

实测：**四个 version 在你这台 `sing-box 1.14.2-reF1nd` 上全部能加载**（version1 是较啰嗦的老格式 1821 KB，v2–v4 均 1671 KB）。

### 7.2 广告表对比：它的 `adrules` 略逊于 anti-AD
拿之前实测的真漏端点逐个比对：

| 目标 | mihomo `adrules`（197,019 条） | anti-AD（99,506 条） |
|---|---|---|
| criteo / outbrain / scorecardresearch / quantserve / adsrvr / rubicon / doubleverify / appsflyer / branch | ✅ | ✅ |
| `sdkmob.com` / `ad.duowan.com` / `uc.cn`（国内 SDK） | ❌ | ✅ |
| **小计** | **11/14** | **14/14** |

→ **主广告表仍用 anti-AD**；`adrules` 的互补价值在于它**含 IP 类广告规则**（anti-AD 只有域名），可作为第二阶段补充。

### 7.3 它的 `cncidr` 正好补上你 geoip 的洞
`cncidr`（version4, 79 KB）有 **17,958 条 CIDR**，且包含 `8.128.0.0/10`（覆盖你实测漏掉的 `8.130.222.0/24`）。
→ 已采纳为脚本的 `--with-cncidr`：给国内 IP 匹配加**第三份独立来源**（本地 geoip/cn + 上游最新 + mihomo cncidr）。

### 7.4 从它的 178 份 YAML 里提炼出的可借鉴点
| 它的做法 | 对你这套的意义 |
|---|---|
| **域名规则在前、IP 规则在后** | ✅ 你已满足（geosite 规则都在 geoip 之前） |
| `fake-ip-filter` 里塞了 `lancache.steamcontent.com`、`*.stun.*`、`xbox.*`、`srv.nintendo.net`、`dns.msftncsi.com` | ⚠️ **能改进**：这些走代理会坏功能（LAN 缓存失效、主机 NAT 类型变差）→ 已提炼成 `must-direct.srs`，脚本 `--with-direct-list` 一条直连规则搞定 |
| `proxy-server-nameserver`（解析节点域名用国内 DoH） | ✅ 你等价物是 `route.default_domain_resolver = dns-direct-ali`（且节点是 IP，本就不受影响） |

| 走 `no-resolve` 减少无谓解析 | sing-box 里由 `sniff` + 规则顺序天然覆盖 |

### 7.5 长期怎么吃这个仓库（两条路）
1. **remote rule_set + `update_interval`**：sing-box 支持 `{"type":"remote","url":"https://raw.githubusercontent.com/HenryChiao/mihomo_yamls/ruleset/singbox/version4/xxx.srs","download_detour":"Proxy"}`，

### 10.2 ⚠️ 测量方法更正（重要）

本文档前面所有"DNS 拦截 = ✅"的判定，**用的是"`dig` 无输出"**，而我把 `dig` 的 **stderr 丢掉了** ——
于是"**REFUSED**"和"**超时**"看起来一模一样。带完整输出复测后真相是：

| 查询路径 | 实际结果 |
|---|---|
| 直连任意解析器（`dig @8.8.8.8 / @223.5.5.5 / @192.168.31.1 doubleclick.net`） | **`status: REFUSED`**（立刻返回，是合法 DNS 响应） |
| 经 `systemd-resolved`（`dig doubleclick.net`） | `communications error to 127.0.0.53#53: timed out`；`resolvectl` 自己说 `server or network returned error: REFUSED` |

即：**sing-box 的 DNS `reject` 语义是 REFUSED**，而 **systemd-resolved 不会把 REFUSED 转告客户端**
（它当作"上游故障"去重试其他上游，最终放弃），于是走系统解析器的应用每个广告域名要**等约 5 秒**才失败。
这不影响"拦截有效"的结论（广告域名确实拿不到解析），但**影响体验**，且 TUN 模式同样存在（只是以前没测出来）。

**修法**：DNS 广告规则由 `reject`(REFUSED) 改为 `predefined` + `rcode: NXDOMAIN` ——
NXDOMAIN 是正常应答，resolved 会如实转告，应用立刻失败并做负缓存。该 fork 已实测支持该写法：
`apply-audit-fixes.sh --nxdomain-ads`（干跑 `check` 通过）。

## 11. 结论：本机只能用 local `cgroup` 数据面（tc / shared 均不可用）— 2026-10-02 11:01 实测

为覆盖 rootless 容器（pasta 把包 splice 进宿主栈、不创建宿主 socket，cgroup socket 钩子看不到），
试了两条路，**都撞在同一处内核能力上**：

```
FATAL start service: start inbound/ebpf[ebpf-in]:
      register TC eBPF TCP listener: operation not supported
```

| 试验 | 结果 |
|---|---|
| `local.data_plane: tc` | ❌ sing-box 启动即 FATAL（上面那行），API 9091 与本地代理口 7892 都连不上；**脚本自动回滚成功**，服务已恢复 |
| `shared`（`data_plane: packet_rewrite`） | ❌ 同一条 TC 路径，**不必再试**（我在 `enable-container-proxy.sh` 里加了守卫直接拦下） |

### 11.1 预检为什么没提前发现（重要）

| 预检模式 | 结果 | 含义 |
|---|---|---|
| `--mode local`（我脚本原先只跑这个） | `preflight_passed`，PASS 37 / FAIL 0 / UNKNOWN 0 | **local cgroup 路径确实全支持** ✓（所以这个结论没错） |
| `--mode all`（含 shared/tc 那 28 项） | **`inconclusive`**：pass 13 / warn 2 / **unknown 36**，required_issues 28 | TC 支持**无法用预检确认**，只能实跑才知道 |

即：`--mode local` 全绿 **不代表** TC 可用。两个脚本现在都会在请求 tc/shared 时先跑
`--mode all`，非 `passed` 就**拦下并给出替代方案**（`--force` 可强行尝试）。

### 11.2 容器的最终结论（已实测）

| 容器网络 | 出口 | 结论 |
|---|---|---|
| rootless 默认（pasta） | 失败（境外直连被墙） | ❌ 无法被接管——pasta 不创建宿主 socket，cgroup 钩子看不到 |
| `--network=host` | `<proxy-exit-ip>` = 代理出口 | ✅ **可行**（容器直接用宿主 socket） |
| rootful 网桥 + shared | — | ❌ 本机内核不支持 TC 路径，不成立 |

**所以：本机（kernel 7.2.8-1-cachyos-bore-lto）的容器透明代理只能靠 `--network=host`。**
（TUN 模式没有这个限制，因为它靠 auto_route 管转发流量；这是切到 eBPF 的唯一实际回退项。）

## 12. 决策：切回 TUN 模式（2026-10-02 11:1x）

§11 证明了本机内核不支持 TC 路径 → eBPF 的 local `cgroup` 数据面**覆盖不到 rootless 容器**
（pasta 不创建宿主 socket），而 TUN 靠 `auto_route` 覆盖转发流量，容器/虚拟机天然被代理。
权衡"eBPF 的新特性"（分应用 UID 策略）与"容器+VM 的完整覆盖"后，选择**回到 TUN**：

| 能力 | TUN | eBPF (cgroup) |
|---|---|---|
| 本机流量接管 | ✅ | ✅ |
| **容器（rootless pasta）** | ✅ auto_route 覆盖 | ❌ 看不到（除非 `--network=host`） |
| **虚拟机 / 共享网络** | ✅ | ❌ 需 TC（本机不支持） |
| 分应用 UID 策略（面板） | ❌ | ✅ |
| 内核依赖 | 需 TUN 设备 | 需 BPF/cgroup（本机满足） |

切换工具：`scripts/switch-to-tun.sh`（只替换 inbound，保留 DNS 故障转移组、`predefined/NXDOMAIN`
广告规则、14 份规则集与包路径；`check` → 备份 → 替换 → 重启 → 健康检查 → 失败自动回滚）。
干跑已验证：生成的配置 `check` 通过、7 个 DNS 服务器 / 14 份规则集 / 11 条路由规则全部保留。

> 备份链完整：`config.*.pre-ebpf.json`（TUN 定义来源）、`config.*.pre-dataplane.json`、
> `config.*.pre-tun.json`（切回 TUN 时自动生成），任何一步都能回退。
