# 12 · 「开机后几分钟网络不稳定」排查报告（2026-10-12）

> 症状（用户描述）：开机后几分钟网络时通时不通，**过一会儿自动恢复**。
> 结论先行：**已知根因已修好且最近 4 次开机 0 次复现**；但本报告查清了它的**真实机制**——
> 它不是崩溃重启，而是 sing-box 主动"暂停网络、等接口就绪后自己醒来"，这正好解释了
> "过一会儿自己就好了"的体感。剩余风险按 §5 排序，逐条给了验证命令。
> **本报告的排查过程未修改任何线上文件。** 唯一落地改动（`urltest.interval` ×4）由用户于
> 2026-10-12 10:11:40 执行，与本报告结论无关，记录见 [`docs/11`](11-配置审查与优化报告-2026-10-12.md) §7.1。
>
> ⚠️ **2026-10-12 下午补充（重要）**：boot+0..300s 窗口确实是 **0 条**，但**换个窗口看完全不同** ——
> 本 boot 有 **1312 条**出站握手超时（`i/o timeout`），其中最近 30 分钟 **717 条且仍在继续**。
> 所以「开机时序」**不是**唯一假设。**§9 是本次新增的核心发现，建议先读 §9 再读 §6/§8。**

## 1. 结论（三段式）

1. **真实机制（本次从上游源码查明，修正了我最初的推断）**：
   启动时若还没有默认路由/默认接口，sing-box **不会退出**，而是
   `pauseManager.NetworkPause()` 并记一条 `missing default interface`，
   等接口事件到达后 `NetworkWake()` 重试。**表现就是"网络先不通，几秒~几分钟后自己恢复"。**
   —— 上游源码：<https://github.com/SagerNet/sing-box/blob/v1.14.2/route/network.go#L526-L537>
2. **修复已生效**：10-08 加的 drop-in `20-network-online.conf`（`[Unit] Wants=network-online.target`）
   把 sing-box 的启动点推到"网络已就绪"之后。**最近 4 次开机**
   （10-11 09:57 / 10-11 16:21 / 10-11 19:10 / 10-12 08:44）：
   `missing default interface` **0 次**、`FATAL`/`panic` **0 次**、非正常退出 **0 次**。
3. **如果仍有体感**，按 §5 顺序查：virbr0 时序窗口（今天裕量只有 4 秒）→ Wi-Fi 省电/驱动 →
   **`connection upload handshake` 需要复核**：本报告早前把它判为「VM/游戏直连大陆端口、与整机无关」，
   但 10-12 下午重新量化发现本 boot 有 **1312 条**、最近 30 分钟 **717 条且仍在继续** —— 见 **§9**，
   那里给出了「这些 IP 到底是你的节点、还是 VM/游戏目标」的**定案命令**。

## 4. 历史故障形态（可作为"下次同类问题"的判据）

10-07 文档记录的原始报错（`docs/05`、`docs/09`、`docs/10`）：

```
network: missing default interface
```

出现时机：10-07 12:53 与 17:08（两次开机早期）。修复动作：新增
`/etc/systemd/system/sing-box.service.d/20-network-online.conf`（300 B）：

```ini

# 2026-10-08 审计：unit 原本只有 After=network-online.target，缺 Wants=，
# 导致 network-online.target 不一定会被拉起，sing-box 可能抢在默认路由之前启动。
Wants=network-online.target
```

回滚方式：删除该文件 + `systemctl daemon-reload`。

**注意区分两类"接口/网络"报错**：

| 报错 | 含义 | 严重性 |
| --- | --- | --- |
| `missing default interface` | 启动期没有默认路由，sing-box 暂停并等待（自愈） | 中（表现为"开机几分钟不稳"） |
| `dial tcp <IP>:<port>: i/o timeout`（`using outbound/direct`） | 某个目标不可达，**与启动无关** | 低（单连接失败） |

## 5. 剩余风险与验证/修复（按可能性排序）

### R1 · virbr0 时序窗口（🟡 唯一有时间窗口嫌疑的项，裕量仅 4 秒）

- **事实**：`inbounds[ebpf].shared.interface = ["virbr0"]`；boot 0 里 libvirtd 就绪 `08:44:31`、
  sing-box 启动 `08:44:35` ⇒ **裕量 4 秒**。unit 对 libvirtd **没有** `After=`/`Wants=`
  （`systemctl show sing-box -p After` 里没有 libvirtd）。
- **机制（已修正）**：fork 的 eBPF 文档写明 shared 接口"**缺接口会重试**"，
  **不是启动失败源**。所以它的影响是"virbr0 尚未就绪的那段时间里，**VM 流量不被代理**"
  （宿主机流量由 `local` cgroup 数据面覆盖，不受影响）。
- **为什么仍值得修**：libvirtd 启动慢的场合（VM 自启、qemu hook、包升级后首次启动）窗口会拉长；
  一个 drop-in 就能把它关掉，代价近乎为零。
- **验证**：
  ```bash
  systemctl show sing-box -p After -p Wants | tr ' ' '\n' | grep -i libvirt   # 现状：无输出
  journalctl -b -0 -u libvirtd --no-pager | head -5                           # 对比启动时刻
  ```
- **修复（提案，未执行）**：`systemd/40-libvirtd-order.conf`

### R2 · Wi-Fi 省电 / mt7921e 驱动（🟡 无法用现有日志排除）

- **事实**：`wlan0` = MediaTek mt7921e；`iw dev wlan0 get power_save` → **`Power save: on`**；
  本次 `dmesg | grep -iE 'mt7921|firmware'` **无输出**（日志已轮转，不能作为"无故障"的证据）。
- **为什么像**：省电模式在链路刚建立、流量稀疏的开机初期会造成周期性丢包/抖动，几秒到几分钟后随
  流量增加而"恢复"——与描述高度吻合。
- **验证**：
  ```bash
  cat /sys/module/mt7921/parameters/* 2>/dev/null | head
  iw dev wlan0 get power_save                 # 现状 on
  journalctl -b -0 -k | grep -iE 'mt7921|mt76|firmware|wlan0'
  ping -i 0.2 -c 300 192.168.31.1 | tail -3   # 开机后立刻跑，看丢包是否集中在前几分钟
  ```
- **修复（需你决定）**：`sudo iw dev wlan0 set power_save off` 试跑，或写
  `/etc/NetworkManager/conf.d/wifi-powersave-off.conf`（`[connection] wifi.powersave = 2`）持久化。
  这属于**无线侧**改动，不在 sing-box 配置范围内，因此只写建议、不生成文件。

### R3 · 开机瞬间 DNS 走 fallback（🔵 秒级，无需动作）

`08:44:26` resolved 切 fallback `9.9.9.9` 时 sing-box 还没起来（08:44:35），查询走直连；
等 sing-box 起来后由 eBPF `dns_mode: hijack` 接管。属正常引导顺序，**不建议改**。
（若担心这 9 秒内的解析质量，可把 `dns.servers.dns-local` 之类本地解析器做成
`route.default_domain_resolver`，但实测没有必要——见 `docs/11` §3.5。**另注意：`dns-local`
在本网络已实测为"收益≈0 且从本机时通时不通"，见 `docs/11` §3.8，不要据此恢复它。**）

### R4 · 冷启动出口选择（✅ 已实测排除）

原本担心"开机头几秒 urltest 还没探测完 ⇒ 没有可用出口"。**干跑实例实测**：
在**零成功探测**（节点域名是占位符 `NXDOMAIN`）的情况下，`clash_api` 里
`Auto.now = 🇯🇵 日本Z01 | IEPL`（非空），全部 selector 也都有 `now`。
⇒ **urltest 在没有历史时会给出一个回退选择，不会出现"无出口"的硬失败。**
（顺带说明：`Auto-Japan` 等组内有节点的情况下，把最稳的节点放在列表靠前更有利。）

### R5 · 那批 `connection upload handshake: ... i/o timeout`（✅ **已定案：本机 sing-box 的 SS 出站连不上 IEPL 中转入口，见 §9.5**）

> ⚠️ **2026-10-12 下午，本节结论被量化证据推翻**：原判「🔵 不是主因 / VM/游戏直连大陆端口」，
> 但重新统计得 **本 boot 1312 条、最近 30 分钟 717 条且仍在继续**。完整数据、两种解释与
> **一条命令定案**见 **§9**。下面保留原始推理，供对照 —— 注意它的「字符串邻居」推断链本身
> 并未被推翻，只是**不足以**支撑「与整机无关」这个结论。

- **事实**：boot 0 的首条 ERROR 是 `08:58:50`（启动后 14 分钟）、boot -1 是 `19:40:32`（启动后 30 分钟）；
  目标全是**大陆 IP + 高位端口**（`入口B:19274`、`入口A:475`、`入口C:14562`、
  `直连目标1:21584`），5.0s 超时，走 `direct`。
- **推断依据**：二进制里 `connection upload handshake` 与 `connection upload closed`、
  `packet upload/download finished`、`TC shared packet-rewrite` 等字符串相邻 ⇒ 属于
  **eBPF `shared`（VM/virbr0 上行）数据面**的日志族。
- **（原）结论**：~~这是虚拟机/客户端里某个应用在连大陆服务器失败，不是整机网络故障，也不是配置问题。~~
  → **作废**。注意本节「走 `direct`」这句也只对 boot -1 的样本成立，本 boot 实测到的是
  `connection upload handshake`（握手层），两者不是同一种失败。
- **现场定位方法**（配置里 `find_process: false`，所以日志里没有进程名）：
  ```bash
  # ① 临时把进程名打进日志（改配置，需重启；用完记得改回）
  #    route.find_process: true
  # ② 或直接看谁在连这些端口（错误发生时立刻执行）
  sudo ss -tnp state established '( dport = :19274 )' 2>/dev/null
  sudo ss -tnp | grep -E '114\.94\.203\.|14\.23\.28\.|35\.75\.3\.'
  # ③ 若是 VM 流量，宿主机上看到的是 sing-box；进 VM 里执行 netstat -ano | findstr 19274
  ```

## 9. ⭐ 真正的持续失败模式：出站握手超时（2026-10-12 新增，推翻「开机时序」为唯一假设）

> **脱敏说明（2026-10-12 晚）**：本节把节点入口 IP 一律写成 `入口A` / `入口B` / `入口C`，把第三方直连目标
> 写成 `直连目标1..5`（**端口、计数、地理与 AS 信息全部保留**，可操作性不受影响）。真实 IP ↔ 代号映射只存在
> 本机 `~/.local/state/sing-box-redaction-map.tsv`，**不进仓库**（与 docs/05、docs/09 的脱敏口径一致）。

§6/§8 一直在 boot 窗口里找证据，结果是 0 条。**换个窗口看就完全不同**：本 boot 里 sing-box 的
`i/o timeout` 有 **1312 条**。注意「**现在仍在发生**」只是 10-12 中午那次的观测 ——
全天普查（见 §9.1.1）显示这是**间歇突发**：最后一条在 **10:28:52**，之后到写这份定案（10:45）没有再出现。

### 9.1 实测数据

| 观测 | 数值 |

### 9.2 这说明什么（区分「事实」与「推断」）——⚠️ 本节结论已被 §9.5 修正

> **2026-10-12 晚补记**：本节的歧义已定案为 **(a) 节点**，且下面那句「TCP 通、隧道不通」**是错的**
> （把两种不同的 syscall 当成了同一种）。完整证据链见 **§9.5**，原文保留供对照。

**~~事实~~（已作废）**：`✅ 可连` 与报错**不是同一个 syscall**。`tcp_fast_open: true` 让 TCP 建连本身
推迟到首次 write（`common/dialer/tfo.go` 的 `slowOpenConn`），所以 `5.0s` 是**到节点的 TCP 建连超时**，
而事后用裸 `connect()` 测「可连」永远不会撞上它。

**⚠️ 先解决一个关键歧义 —— 这一步必须先做，否则下面全是猜**

这些 IP **都在中国大陆**（上海电信 / 广东电信），而配置里的节点名字全是「香港 / 日本 / 新加坡」。
所以它们只能是两种东西之一：

- **(a) 你的代理服务器地址**：如果这些节点是 **IEPL 中转**（客户端先连国内入口 IP，再走专线出境），
  那 CN IP 完全合理 —— 节点名里的「`| IEPL`」正是这个意思。→ 成立则是**节点 / 握手层故障**。
- **(b) VM / 游戏等直连大陆服务器的目标地址**：本机有 `virbr0`（libvirt）+ eBPF `shared` 数据面在拦下游流量，
  §1.3 早前正是按这个解释把它判为**无关**。→ 成立则**与本机代理无关**。

**✅ 此歧义已定案为 (a)，而且不需要读真实配置**：① 仓库脱敏快照里 11 个出站的 `type` 全是 `shadowsocks`；
② 报错里的 distinct 端点恰好 11 个，且与 `direct` 路由的失败地址**零重叠**（完整证据链见 **§9.5**）。
下面两条命令与推理保留供对照 —— 现在跑只会再次确认 (a)。

**（当时）我无法自己定案**：真实配置是 `root 0600`（我读不到），Clash API 需要 secret。**你跑这两条就能定案**：

```bash

sudo grep -c '114\.94\.203\.35' /etc/sing-box/config.json
```

**推断（尚未验证，标为假设）**，按可能性排序：

1. **若 (a) 成立 → 节点侧问题**：某几个节点负载满 / 被限速 / 被墙，TCP 端口还开着但协议层不响应。
   证据支持：失败高度集中在 1–2 个目标（`入口A:806` 占 501/717 ≈ 70%）。
2. **`tcp_fast_open: true` 与中间盒冲突**：11 个 shadowsocks 出站**全都开了 TFO**。TFO 把首包塞进 SYN，
   若路径上有中间盒丢弃 SYN 携带的数据，就会出现「TCP 建连成功但首包永远不到」→ **与本例症状完全吻合**。
   验证方法见 §9.3 的实验 A。
3. **urltest 把流量留在了一个已劣化的节点上**：`Proxy`/`Auto` 都是 `interrupt_exist_connections: false`，
   已建连接不会因切换而重连；且 urltest 只按「延迟」排序，节点半死时未必及时剔除。

**排除**：「本机开机与 `sing-box` 的启动顺序」、「virbr0 未就绪」、「DNS 未就绪」——
这些只影响 boot 窗口，而 boot 窗口是 0 条。

### 9.5 ✅ 定案（2026-10-12 晚）：是本机 sing-box 的 SS 出站连不上 IEPL 中转入口

**结论**：这些报错**不是** VM/游戏直连，**就是代理链路本身**。发出方 = 本机 sing-box 的 `route/conn.go`
上传路径；`dial tcp <IP>:<PORT>` 里的 `IP:PORT` = **11 个 shadowsocks 节点（IEPL 中转入口）的 `server:port`**；
错误语义 = **到该入口的 TCP 建连 5s 超时**，而不是「协议层握手失败」。
