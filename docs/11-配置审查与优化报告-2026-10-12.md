### 3.3 `sing-box check` 与"check 通过 ≠ 能跑"（E2/E3）

```
emo$ sing-box check -c config.sanitized.json
FATAL prepare eBPF self-bypass: create eBPF self-bypass socket map: creating map: map create: operation not permitted
      (MEMLOCK may be too low, consider rlimit.RemoveMemlock)      → exit 1   ← 纯权限，非配置
emo$ sing-box check -c <去掉 ebpf 入站的同一配置>                    → exit 0   ← 其余全部合法（17 份规则集全部加载）
emo$ sing-box check -c config/config.new.json（去 ebpf）             → exit 0
root# systemd 的 ExecStartPre 也是这条 check，且现役服务在跑         → 全配置（含 ebpf）root 下合法
```

本次抓到一个**只有运行期才暴露**的坑（出现在我的第一版候选配置里，不是现役配置）：

```
dns server 写 { "type":"udp", "tag":"dns-local", "detour":"direct" }
  → sing-box check : exit 0（不报错）
  → sing-box run   : FATAL start service: start dns-transport:
```

即 **DNS server 的 `detour` 不能指向"空的 direct 出站"**，而 `check` 不查这一点。候选配置因此
**省略 `detour`**（默认直连），并用 E3 干跑验证过能启动。

> 教训：改 DNS 段之后必须真实启动一次。应用脚本自带这一步。

### 3.7 仍然不确定的（明确标注）

### 3.8 落地前实测：为什么 P2-1 被撤回（2026-10-12）

原 P2-1 的理由是"`.lan/.home` 会落到 `final: dns-proxy`，被 Cloudflare 经代理解析，既慢又必然
NXDOMAIN，所以该加本地域直查"。**按交付项 4"先测试后更新"实测后，这个前提在本网络不成立**：

| 检查 | 命令 | 实测结果 | 含义 |
| --- | --- | --- | --- |
| 网络有没有宣告"本地域" | `nmcli -f IP4.DOMAIN device show wlan0` | 空 | DHCP 没下发搜索域 ⇒ 本网络没有"本地域名空间"这个概念 |
| 有没有内网主机名 | `grep -vE '^#\|^$' /etc/hosts` | 只有默认注释行 | 本机也不认识任何内网名 |
| 本地解析器认不认 `.lan` | `dig +short test.lan @192.168.31.1`（及 `nas.lan`/`router.lan`） | `NXDOMAIN`（有时直接超时） | 加规则后**答案还是 NXDOMAIN**，只是换了谁来答 |
| 本地解析器到底是什么 | `dig +short CH TXT id.server @fd00:6868:6868::1` | `"hkg09"` | 这是 **Cloudflare 香港 PoP 名** ⇒ 它只是把 CH 查询转发给上游的**纯转发器**，不持有本地区（`@192.168.31.1` 查同一项返回空/超时） |
| 该解析器可靠吗 | `dig +short baidu.com @192.168.31.1`（`+time=2` 批次） | 5/5 超时；换 `+time=5 +tries=3` 才偶尔有答；TCP/53 超时；ICMP 100% 丢包 | 这个地址的 DNS 从本机**时通时不通** |

据此撤回 P2-1，三条理由：

1. **收益≈0**：本网络没有本地域名空间，`dns-local` 对那 4 个后缀的回答与现状一样是 NXDOMAIN。
2. **风险>0**：`192.168.31.1:53` 从本机不可靠 ⇒ 一旦有程序真的去查这些后缀，会从"立刻 NXDOMAIN"
   变成**卡到 `dns.timeout: 10s` 才失败**——把"必然失败但很快"换成"可能失败且很慢"。
3. **顺手修正原证据的一处笔误**：§2.1 原写"`dns.servers` 里已有 `dns-local` 却无人引用"，
   但脱敏快照的 7 个 server 是 `hosts-bootstrap`/`dns-proxy-cf`/`dns-proxy-google`/`dns-direct-ali`/
   `dns-direct-tencent`/`dns-proxy`/`dns-direct`，**没有** `dns-local`——原建议其实是"新增一个 server"。
   而且这份 `dns-local` 是被**上一轮审计主动删掉**的：[`README.md`](../README.md) 的 10-02 时间线写着
   `10:12` 审计修复"…删 2 条冗余规则、删 `dns-local`"，[`scripts/README.md`](../scripts/README.md) 里
   `apply-audit-fixes.sh` 的说明同样是"清理冗余规则与 `dns-local`"。即它当年就是"没人引用的冗余项"，
   本次撤回与历史结论一致。

**不夸大、明确标注的部分**：本机所有发往 53 端口的探测都可能被本机自己的 eBPF
（`ebpf-in.local.dns_mode: hijack`）截获，`bypass_private_address: true` 是否覆盖 DNS 劫持路径
**未从源码确认**。若探针其实被 sing-box 接管，那么"解析器不可靠"反映的是**探针路径**而非路由器本体，
第 2 条风险按"低但非零"对待即可。第 1、3 条不依赖探针路径（**没有本地域名空间**、**上游是 Cloudflare
转发器**），足以支撑撤回。

**产物的相应改动**：`config/config.new.json` 删掉了 `dns-local` server 与新 `dns.rules[0]`
（现 660 行；唯一改动 = 4 处 `urltest.interval: 5m → 3m`，与脱敏快照逐字段比较**其余全部 IDENTICAL**）；
落地脚本默认不动 DNS，只有 `--with-dns-local <IP>` 才加，且**先探测该解析器 3 次、3/3 成功才写**。

## 6. 开机后几分钟网络不稳定（对应交付项 5）

- **真实机制（本次修正）**：抢在默认路由之前启动时，sing-box 会 `NetworkPause()` 并记
  `missing default interface`，等接口事件到达后 `NetworkWake()` 自愈——**是"网络暂停后自愈"，
  不是崩溃重启**。这正好解释了"开机后几分钟不稳、过一会儿自己好"。
- 10-08 用 `20-network-online.conf`（`Wants=network-online.target`）把启动点推到网络就绪之后：
  boot 0 里 `network-online` 与 sing-box **同一秒（08:44:35）**启动；**最近 4 次开机
  `missing default interface` 0 次、FATAL 0 次**。
- 实测时间线（boot 0）：开机 08:44:16 → resolved 切 fallback 08:44:26 → libvirtd 08:44:29–31
  （virbr0/dnsmasq 就绪）→ `network-online` + sing-box **08:44:35**（比 libvirtd 晚 **4 秒**）→
  boot+0..300s 窗口 **0 条告警** → 首条 ERROR **08:58:50**（= boot+14m，**在窗口之外**）。
- 若仍有体感，按此顺序查：**P3-3 出站握手超时（已定案 = 到节点入口的 TCP 建连超时、突发式 → `docs/12` §9.5）** →
  P2-4 virbr0 时序窗口（裕量 4 秒）→ Wi-Fi 省电（`wlan0` `power_save: on`）。
  ~~别把 `connection upload handshake` 当成主因~~ —— **该判断已于 10-12 晚定案推翻：它就是代理链路本身
  （11 个 SS 节点的 IEPL 入口间歇性连不上），不是 VM/游戏直连**（证据链见 `docs/12` §9.5）。

## 更正（2026-10-12 晚 · 实测）

本文档 §P3-6（以及 `systemd/README.md` 提案 C、`config/config.new.diff.md` 第 209 行）
写"规则集由 `emoeem-repo-update.timer` 自动更新，今天 08:45:57 已跑"——**这个前提是错的，
据此得出的"经核对已降级"不成立**：

- journal 里 `emoeem-repo-update.service` **4 次触发、4 次失败、0 次成功**，每次都是
  `Git repository not found: /var/lib/emoeem-repo`（该目录不存在）；当时它还是
  `systemctl --failed` 里**唯一**的一项，把真正的开机问题盖住了。
- 规则集包实际由 `pacman` 安装：`/var/log/pacman.log` 里
  `[ALPM] upgraded sing-box-rule-sets (20261010-1 -> 20261011-1)` @2026-10-11T14:56:07、
  `sing-geosite-rule-set` @2026-10-10T14:24:29。即**用户手动 `pacman -Syu` 时随 `[emoeem]`
  滚动 release 更新**，不是定时任务。该 timer 的安装器已在 `11d8cde` 被删除，
  机器上那套是残留；清理用 `~/pkgbuild-source/scripts/remove-legacy-repo-update.sh`
  （默认 dry-run，`--apply` 才删）。

所以：包**确实是包管理的**，但**不是自动更新的** —— 那 2139 份的新鲜度取决于你是否记得
跑 `pacman -Syu`（`ffmpeg-full` 2.7→2.8 卡在本地索引上就是这个原因）。是否要为"索引/包
自动刷新"另做一套（只刷 db、不装包、校验 `SHA256SUMS`）是**尚未定案**的新问题，
不在本文档结论范围内。另外，同一类故障（DNS 缓存里落一条错误的否定应答）已由新增的
`scripts/sing-box-dns-watchdog.sh` + `systemd/sing-box-dns-watchdog.{service,timer}` 兜住。
